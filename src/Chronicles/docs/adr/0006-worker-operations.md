# ADR 0006: Операционная модель фонового воркера Chronicles

## Статус

Принято

## Контекст

`Chronicles` обновляет витрину асинхронно и не должен блокировать игровой runtime.
Нужно выбрать понятную операционную модель:

- как часто выполнять import и projection;
- где фиксировать прогресс обработки;
- как логировать и диагностировать процесс;
- как расширять обработку новыми номинациями.

## Решение

Используется отдельный worker-процесс, который в каждом цикле выполняет два шага:

1. `Inbox import`
   Забирает новые `GameSessionCompletedIntegrationEvent` из внешнего outbox и складывает их в локальный inbox.
2. `Projection`
   Обрабатывает непрочитанные inbox-сообщения и обновляет витрину хроник.

Worker не применяет миграции и не seed'ит данные на старте. Схему подготавливает отдельный `Migrator`, после чего worker только выполняет runtime pipeline.

### Идемпотентность

- `InboxMessage.Id` совпадает с `OutboxMessage.Id`;
- повторный import не создаёт дубликатов из-за проверки существующего inbox-сообщения;
- прогресс чтения source outbox хранится в `chronicles.import_cursors`;
- локальная обработка помечает сообщение через `ProcessedAtUtc`.
- сообщения с повторяющимися ошибками получают retry delay и затем переводятся в dead-letter.

На текущем этапе worker считается single-instance. Конкурентная обработка одного inbox несколькими worker-ами не поддерживается намеренно, чтобы не усложнять рабочую версию.

### Логирование

Логирование реализовано через source-generated `LoggerMessage`.

### Расширение номинаций

Новые номинации добавляются стратегиями `IChronicleNominationProjector`, а не через разрастание одного большого обработчика.

## Последствия

### Плюсы

- import и projection разделены;
- worker остаётся простым orchestration-слоем;
- ошибки import и projection можно диагностировать на уровне inbox/outbox сообщений;
- переход на брокер сообщений не потребует переписывать projection-логику.

### Минусы

- текущий importer остаётся polling-процессом;
- transport-доставка и projection пока выполняются в одном worker-сервисе;
- для больших объёмов в будущем могут понадобиться broker, claim/lease и отдельные consumer-пулы.
