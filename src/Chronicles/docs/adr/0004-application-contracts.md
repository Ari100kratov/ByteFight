# ADR 0004: Application-контракты и общие абстракции

## Статус

Принято

## Контекст

В основном приложении уже существуют application-абстракции для `Command`, `Query` и handler-модели.
Локальное дублирование тех же интерфейсов внутри `Chronicles` создаёт проблемы:

- дублируется контрактный код;
- одинаковые по смыслу типы живут в разных сборках;
- развивать cross-cutting механики становится сложнее.

## Решение

Общие messaging-абстракции вынесены в `SharedKernel.Messaging` и переиспользуются из разных bounded contexts.

При этом внутри самого `Chronicles` use-case слой организован не как обязательный локальный CQRS pipeline для всего подряд, а как явные application-сервисы:

- `IChroniclesProjectionService`
- `ICharacterChroniclesReader`
- `IChroniclesLeaderboardReader`

Такой подход выбран потому, что:

- не все сценарии требуют полной команды/запроса как отдельного типа;
- сервисные контракты проще для внутренней orchestration-логики воркера;
- при необходимости внешний API всё равно может адаптировать их к любому transport-слою.

## Последствия

### Плюсы

- убрано дублирование базовых application-контрактов;
- общие abstractions живут в одном месте без привязки к основному `Application`;
- `Chronicles` не перегружен локальной инфраструктурой ради простых use-case'ов.

### Минусы

- `SharedKernel` становится общей точкой расширения для минимальных cross-context контрактов;
- нужно аккуратно следить, чтобы в него не утекала доменная логика конкретных bounded contexts.
