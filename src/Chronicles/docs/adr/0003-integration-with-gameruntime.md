# ADR 0003: Интеграция Chronicles с GameRuntime

## Статус

Принято

## Контекст

`Chronicles` должен получать факты о завершённых игровых сессиях из другого bounded context.
Ключевые требования:

- слабая связность между контекстами;
- отсутствие ожидания хроник в основном игровом потоке;
- стабильный интеграционный контракт;
- возможность отдельно организовать backfill и пересчёт истории.

## Решение

Основная интеграционная модель:

- `GameRuntime` формирует `GameSessionCompletedIntegrationEvent`;
- событие пишется в `OutboxMessage` в той же транзакции, где фиксируется завершение сессии;
- downstream-потребитель `Chronicles` импортирует событие в свой `InboxMessage`, не изменяя source outbox;
- дальнейшая проекция работает уже локально, внутри `Chronicles`.

Participant snapshot в событии содержит не только технические идентификаторы, но и отображаемые данные на момент боя:
имя персонажа, имя/фамилию пользователя, класс и специализацию персонажа.
Это intentional denormalization: лидерборды не должны на каждый запрос ходить в Auth/Game, а история должна оставаться понятной после будущих изменений профиля или персонажа.

Контракт события живёт отдельно от доменной модели `GameRuntime` в `IntegrationContracts`.
Это означает, что между bounded contexts не передаются EF-сущности и внутренние доменные типы `GameRuntime`.

`GameRuntime` остаётся владельцем outbox. `Chronicles` хранит собственный progress cursor в своей БД и не использует `processed_at_utc` source outbox как consumer checkpoint.

## Почему не прямое чтение БД

Прямое чтение чужой БД:

- быстро для прототипа;
- удобно для разовой догонки;
- но делает `Chronicles` зависимым от схемы хранения `GameRuntime`.

Такой вариант не принимается как production-модель.

## Почему не HTTP API как основной канал

Клиентский HTTP API:

- не предназначен быть внутренним транспортом для проекций;
- плохо подходит для batch/import сценариев;
- создаёт синхронную бизнес-связность там, где нужна асинхронность.

## Роль gRPC

`gRPC` может быть полезен:

- для внутреннего export/backfill API;
- для специализированной сервисной выгрузки истории;
- для административных сценариев пересчёта.

Но `gRPC` не выбран как основной production-поток хроник.

## Роль backfill

Backfill считается отдельным механизмом, а не частью production ingestion:

- production получает только новые события;
- first-run backfill создаёт недостающие `GameSessionCompletedIntegrationEvent` в `GameRuntime` outbox для уже завершённых сессий;
- будущий расширенный backfill может читать историю через отдельный export contract;
- это позволяет не смешивать долгий пересчёт с регулярным import pipeline.

## Роль Web.Api

Пользовательский read API хроник на текущем этапе публикуется через существующий `Web.Api`.
Это не делает `Web.Api` владельцем обработки хроник: API только читает витрину `Chronicles`, а ingestion/projection остаются в `Chronicles.Worker`.

## Последствия

### Плюсы

- bounded contexts отделены стабильным контрактом;
- `Chronicles` можно развивать независимо;
- transport можно менять без переписывания projection-логики;
- будущие сервисы `Notifications`, `Analytics`, `Achievements` могут использовать тот же outbox-поток.

### Минусы

- требуется отдельная инфраструктура интеграции;
- нужно поддерживать контрактную совместимость `IntegrationContracts`;
- backfill требует отдельного проектирования.
